# GraspDev

VS Code のサイドバーで動くコーディングエージェントです。コードベースを自分で調査し、質問への回答や指示された変更の実装を行います。モデルは OpenAI API の `gpt-6-luna` を使用します。

実装した変更はすぐにはファイルへ書き込まず、**変更の理由と影響を、利用者が自分で確かめながらたどってから反映**します ([理解してから反映する](#理解してから反映する))。

## 使い方

Node.js 20 以上が必要です。

```bash
npm install
npm run build
```

1. VS Code でこのフォルダを開いて `F5` (Run Extension)。拡張機能を読み込んだ別ウィンドウが開きます。
2. そのウィンドウで対象のフォルダを開き、アクティビティバーの吹き出しアイコンから GraspDev を開きます。
3. 初回は設定パネルが表示されるので OpenAI API キーを入力して保存します (VS Code の SecretStorage に保存)。
   あとから変更するときは、ビュー右上の歯車ボタンで同じパネルを開きます。
4. 質問や指示を送信します。

会話はメモリ上にのみ保持され、保存されません。ウィンドウを閉じる (または再読み込みする) と破棄されます。

## 機能

| ツール | 内容 | 確認 |
|---|---|---|
| `Read` | 行番号付きでファイルを読む (範囲指定可) | 不要 |
| `Glob` | glob でファイルを探す (更新日時順、.gitignore 尊重) | 不要 |
| `Grep` | ripgrep による正規表現検索 (VS Code 同梱の rg を使用) | 不要 |
| `Edit` | 完全一致の文字列置換。事前の Read と一意性を要求 | 不要 (ワークスペース外は必要) |
| `Write` | ファイルの作成・上書き | 不要 (ワークスペース外は必要) |
| `Bash` | シェルコマンド実行 (タイムアウト付き) | 必要 |
| `TodoWrite` | 作業のタスクリスト表示 | 不要 |

- 読み取り専用ツールだけの呼び出しは並列実行されます。
- Windows では `Bash` は cmd.exe で動きます。モデルにはその書き方 (`.\mvnw.cmd test` など) を伝え、出力が UTF-8 でなければ従来の文字コード (日本語環境なら Shift_JIS) として読みます。
- ワークスペース内の編集に確認は要りません (変更は取り置かれ、手順をたどり終えてから反映するため)。
- 権限モード (入力欄下のセレクタ): コマンド実行前に確認 / すべて自動許可。
  確認時に「このセッション中は常に許可」を選ぶと、ツール単位 (Bash はコマンドの先頭語単位) で記憶します。
- ワークスペース直下の `AGENTS.md` (無ければ `CLAUDE.md`) をプロジェクト指示として読み込みます。
- 開いているファイルと選択範囲を文脈としてモデルに渡します。
- 入力トークンが閾値を超えると会話履歴を自動で要約します。

## 理解してから反映する

コーディングエージェントに任せきりにすると、変更の理由や影響の範囲が利用者に見えなくなります。
GraspDev は、実装の完成度を保ったまま、利用者が判断しながら変更を受け入れられるようにします。

### 流れ

1. **決めるのは利用者。** 受け入れ条件が一つに決まらない依頼 (解釈や作り方が複数あり、動作や範囲が変わるもの) では、
   エージェントが調査のあと、ファイルを変える前に「実装の前に決めること」を選択肢つきで尋ねます (`AskUser` ツール。1〜3問、おすすめの案が先頭、自由記述も可)。
2. **実装は今までどおり最後まで行う。** エージェントは実ワークスペースで調査・編集・テスト実行まで終えます。
   エージェントのループ (`src/core/agent.ts`) は理解の仕組みを知りません。この仕組みが足すのは、上の `AskUser` ツールとその使い方の指示だけです。
3. **確定した変更を取り置く。** 実行前の状態と比べて変わったファイルを集め、ファイルを変更前に戻します。
   git 管理下では、コマンドが直接書き換えたファイル (フォーマッタ、`npm install` など) も対象です。
4. **手順と問いを組み立てる。**
   - 変更を宣言ごとのステップに分け、依存される側から並べます (データ・型 → 中核の処理 → 呼び出し元 → 画面 → テスト → 設定 → 説明文)。
   - 変わった宣言や文字列キーを使っている場所を検索し、それぞれを「変更が必要 / 変更は不要」に分けます。
     エージェントが実際に見た行の記録と照合し、読まれていない場所には判断を付けません。
   - 理由 (なぜ変えたか・なぜ変えなかったか) と受け入れ条件は、作業したエージェント自身の会話の複製に聞きます。読んでいない場所の理由は採りません。
   - 問いのコードは確定した変更後のコードから組み立てます。モデルが決めるのは「どの行のどの部分を空欄にするか」だけです。
   - 問いにするステップは「たどり方」ごとの上限までにし、影響の及ぶ場所が多い変更を先に選びます。それ以外のステップは、差分と1行の理由で見せます。
   - 答える前に見える文章に、答え (空欄に入るコード・影響の及ぶ場所) が含まれないかを機械的に判定し、含まれていれば書き直させます。
     それでも残れば、答えを含む文だけを除きます (伏せ字にはしません)。
   - 文章は「実装しました」という報告ではなく、利用者がこれから実装する手順として書かせます。報告の形 (「〜ました」など) が残っていれば、機械的に見つけて書き直させます。
   - たどり方が「コードを追う」「影響を予想する」のときは、その言葉だけでは分からない表現 (プロジェクト固有の名前・前提を要する言い方) に、それが何でどこにあるかを補わせます。
5. **1ステップずつたどる。** 最初の「要件の整理」に、これからたどるステップの一覧が出ます (問いのあるステップには「問い」の札が付きます)。
   各ステップで答える前に見せるのは、見出し・目的の1行・コード・問いだけです。問いにはすべてボタンで答えます。
   どの問いにも「わからない」があり、当て推量をせずに先へ進めます。
6. **まとめる。** 変更の流れを説明する文章の、部品の名前 (関数・型・ファイル) を選んで埋めます ([まとめ](#まとめ-仕組みの説明の空欄))。
7. **たどり終えてから反映する。** 最後の「変更の全体像」で、受け入れ条件とそれに対応するステップ、反映するファイル、
   動作確認 (何をどこまで確かめてあるかの説明と、実行したコマンドの結果) を見て、反映か破棄を選びます。

仕組みについての質問 (ファイルを変えない依頼) では、回答を先に見せず、エージェントが実際に読んだコードの要所を空欄にした問いをたどり、
仕組みの説明をまとめてから、回答を開示します。

実行中、コマンドや編集の呼び出しは会話に出しません。いま行っている作業を、入力欄の上に1行で示します
(例: 「ファイルを読んでいます: src/price.ts」「コマンドを実行しています: npm test」「コマンドが失敗しました: …(Exit code: 1)」)。
コマンドの実行許可も、入力欄の上で確認します。

### 何を「理解」とするか

ここでの理解は、**部品の役割と、そのつながりを自分で再構成できること**です。
人に仕組みを説明できることも、変更がどこに及ぶかを予想できることも、この同じ力の現れとして扱います。
問いは、この力を確かめるものだけにし、読む量は次の基準で抑えます。

- 答える前に見せるのは、次の判断に必要なものだけ (目的の1行・コード・問い)。どの条件・どのステップのための変更かは、文章ではなく札で示します。
- 答えたあとにその場に出すのは、予想が外れたこと (または「わからない」) を正すものだけ (その空欄の理由と、選んだものが違う理由)。
- それ以外は、必要なら見られるよう「くわしく」として折りたたんで添えます。
  - この変更の役割と、変更前との違い (問いのコードには変更後しか出ないので、変更前を見られるのはここだけです)。
    変更の理由は、目的の1行と空欄の理由で言っているので繰り返しません。
  - ほかの場所への影響を、どう確かめたか。変えなかった場所には、判断の根拠になる行そのものを添えます。
    どの場所にも同じ文が付いた理由と、作業の中で読まれなかった場所は出しません。
- 差分の省略は、変更と変更の間が離れているときだけにします (数行なら省略せずに見せ、先頭と末尾の省略は書きません)。
  新しいファイル・消すファイルは最初の8行だけを見せ、残りは求めたときに開きます。新しいファイルはまだ開けないので、リンクにしません。

問い・ヒント・解説は、どこに出ても同じ見た目です。左の線の色と先頭の札で区別します
(問い = 青 / ヒント = 灰色の破線。求めたときだけ出る / 解説 = 緑または黄。答えたあとに出る)。
コードの空欄を押すとその選択肢へ、選択肢を選ぶと空欄へ、画面が動いて短く光ります。次のステップへも、なめらかに移ります。

### たどり方ごとの違い

設定の「たどり方」は、その人にとって何が見えていないか (= 何を確かめたいか) で選びます。経験の長さではなく、することの名前にしています。
言葉づかいだけでなく、問いの数と形、見せる情報が変わります (`src/understand/lib/level.ts` の `LevelProfile`。コードの中では beginner / intermediate / advanced)。

| | コードを追う | 影響を予想する | 変更を判断する |
|---|---|---|---|
| 見えていないもの | コードそのもの | 部品どうしのつながり | エージェントの判断 |
| 確かめること | 処理を追える | 変更の及ぶ先を予想できる | 変更を受け入れてよいか判断できる |
| 空欄 (1つのコードあたり) | 1つ・3択 | 2つまで・4択 | 2つまで・4択 (分かれ目が無ければ作らない) |
| 問いにするステップ | 3つまで | 4つまで | 2つまで |
| 変更の影響の問い | 変える必要がある行を、実際の行から選ぶ | 変更が必要になる場所を、候補から選ぶ | 変えなかった場所を、そのままにしてよいか判断する |
| 受け入れ条件 | 見せない | 見せる | 見せる |
| 進み方 | 1画面に問いは1つ (答えると次の問いが出る) | 1ステップずつ | 問いの無いステップは止まらずに続けて見せる |
| まとめの空欄 | 1つ | 2つまで | 3つまで |

- **コードを追う: 具体的な値で問う。** 空欄のある関数が「数値の引数だけを使った四則演算をそのまま返す」形 (JS / TS) なら、
  コードの選択肢の代わりに「amount が 100、rate が 0.1 のとき、calcPrice が返す値はどれですか?」と値で問います。
  値は、選択肢のコードを式に入れてシステムが計算します (モデルには計算させません。利用者のコードも実行しません)。
  引数に入れる値は、テストに同じ関数の呼び出しがあればそこから、無ければモデルが挙げた例を使います。
  テストに書かれた期待値と計算が食い違うとき・計算できない書き方のときは、値では問わず、コードの選択肢のままにします。
- **コードを追う: モデルが問いを作れなかったステップ**には、「この行が呼んでいる関数はどれか」を、実際のコードにある関数だけから機械的に作ります。
- **変更を判断する: 判断に正誤は付けません。** 変えなかった判断が正しいかは機械的に確かめられないので、なぜその場所を確かめるのか
  (何が変わったので、ここも合わせる必要がありうるのか)・その行・変えなかった理由 (あれば) を見せ、
  「このままでよい / 変更が要る / 確認が足りない」から選びます (依頼全体で3か所まで。作業の中で読まれていない場所が先)。
  画面では、誰が作業したかには触れません (判断するのは利用者です)。
  「このままでよい」以外を選んだ場所は、最後の「変更の全体像」に「気になった場所」として残り、確認の依頼の文を入力欄に入れられます (送るのは利用者です)。

変更の影響の問い (コードを追う・影響を予想する) は、実際に変更が必要になった場所があるステップにだけ出します。
違う選択肢にするのは、変わった名前をどこにも使っていない場所だけです (変更が不要だった場所・読まれていない場所は、必要とも不要とも言い切れないため)。

### まとめ (仕組みの説明の空欄)

ステップをたどり終えると、変更の流れ (質問のときは、答えになる仕組み) を説明する1〜2文の中の、部品の名前を選んで埋めます。
埋めた文章は、人に説明するときの材料として残ります。

- 空欄にするのは、実際のコードに宣言がある名前 (関数・型) とファイルだけです。場所はモデルではなく、システムが決めます。
- 違う選択肢にするのは、説明に出てくるどの部品とも、コードの上でつながりの無い部品だけです
  (つながりのある部品は、文章の書き方しだいで当てはまりうるので、違うとは言い切れないため)。
- 違う選択肢を2つ用意できない小さなコードベースや、部品の名前が出てこない説明では、問いにせず文章をそのまま見せます。

### 続きの依頼・破棄

- 手順の途中で続きの指示を送ると、そこまでの変更を踏まえて作業を続け、終わったら変更全体をあらためてたどります。
- 破棄すると、ファイルは変更前のままになり、次の依頼でモデルにそのことを伝えます。
- 手順を作ったあとに、利用者が対象のファイルを書き換えていた場合も、たどり直しにはしません。
  変更と重ならない場所の書き換えなら、両方を残して反映します。同じ場所が書き換えられていたら、何も書き込まずに知らせ、
  そのファイルを元に戻して反映し直すか、「上書きして反映する」(あとから書き換えた内容は失われます) かを選べます。
- 作業が途中で止まった (中断・エラー) ときや、手順を組み立てられなかったときは、差分をそのまま示して反映か破棄を選べます。

### 設定

設定パネル (ビュー右上の歯車) で切り替えます。

| 項目 | 既定 | 内容 |
|---|---|---|
| たどり方 | 影響を予想する | コードを追う / 影響を予想する / 変更を判断する。問いの数と形・見せる情報・用語の扱いが変わります ([たどり方ごとの違い](#たどり方ごとの違い)) |
| テストモード | オフ | API を呼ぶ前の確認と、会話全体を画像で保存するボタン ([出力パネルとテストモード](#出力パネルとテストモード)) |

### 出力パネルとテストモード

VS Code の「出力」パネルで「GraspDev」を選ぶと、API を呼ぶたびに、モデルと入力・出力のトークン数、プロンプトキャッシュに当たった入力トークン数が1行で記録されます。送った内容は記録しません。

```
12:00:02 gpt-6-luna 入力3,310(キャッシュ2,816) 出力48
12:00:05 gpt-6-luna エラー API error 400: ...
```

設定パネルで「テストモード」(既定はオフ) をオンにすると、開発・検証向けに次が加わります。

- API を呼ぶたびに、目的・モデル・想定入力トークン数をダイアログで確認する。「この処理では以降確認しない」で、その依頼が終わるまでの確認を省ける。取り消すと、その処理は API を呼ばずに止まる
- 入力欄の下に「画面を保存」が出る。スクロールで隠れている部分も含めた会話全体を PNG にして、保存ダイアログで選んだ場所に保存する。
  初期位置は前回保存したフォルダー (初回は拡張機能の保存領域の `screenshots/`。Windows なら `%APPDATA%\Code\User\globalStorage\local.grasp-dev\screenshots`)。保存後の通知の「フォルダーを開く」で、保存した場所を開ける

### 制限

- 実行中は実ファイルが一時的に書き換わります (終わると変更前に戻ります)。取り置いている間、ファイルは変更前の内容です。
- ワークスペース外への副作用 (データベースの変更、グローバルなインストールなど) は戻せません。作業の中で行われたコミットも残ります。
- git 管理でないフォルダでは、コマンドが直接書き換えたファイルを拾えません (Edit / Write の分だけを扱います)。
- 影響の検索は名前の単語一致です。同じ名前の別のものも拾い、言語サーバほど正確ではありません。宣言の解析は TS / JS / Java を想定しています。
- 選択肢から選べることと、何も無いところから説明できることは同じではありません。まとめの問いが確かめるのは「どの部品が関わるか」までで、
  部品の順序や役割の取り違えは確かめられません。
- 値で問えるのは、数値の四則演算をそのまま返す JS / TS の関数だけです。それ以外は、コードの選択肢で問います。
- 理由は事後の聞き取りなので、エージェントの実際の判断と一致する保証はありません。場所と差分は機械的に求め、読んでいない場所の理由は採らないことで抑えています。
- バイナリや 1MB を超えるファイルは取り置けず、書き換わったまま残ります (最後に一覧で示します)。

## 設定

ユーザーが変更できるのは API キー・権限モード・たどり方・テストモードだけです。それ以外 (モデル、API方式、最大ターン数など) は
`src/config.ts` の固定値で動作します。挙動を変える場合はこのファイルを書き換えてビルドし直します。

## 設計

```
src/
  config.ts    固定の動作設定
  core/        vscode 非依存のエージェント本体 (Node 単体でテスト可能)
    agent.ts         モデル呼び出し → ツール実行のループ、中断、自動要約
    permissions.ts   権限モードと許可判定 (UI は ask 関数を渡すだけ)
    systemPrompt.ts  システムプロンプトの組み立て
    types.ts         プロバイダ非依存のメッセージ/イベント型
  providers/   LLM バックエンド (LLMProvider を実装して ProviderRegistry に登録)
  tools/       ツール (Tool を実装して ToolRegistry に登録)
  understand/  理解してから反映する仕組み (vscode 非依存。エージェントのイベントを聞くだけで、本体には手を入れない)
    recorder.ts    作業の記録 (読んだ行・検索・コマンド・編集)
    changeSet.ts   実行前の状態の控え、変わったファイルの収集、取り置きと反映
    steps.ts       確定した変更をステップに分けて並べる
    impact.ts      影響が及びうる場所の収集と判定
    lesson.ts      理由の聞き取り、問いの組み立て、画面に渡す形
    reading.ts     仕組みの質問での、読んだコードからの問い
    session.ts     進行役 (取り置き → 提示 → 反映 / 破棄)
    lib/           問いの検証・選択肢・答え漏れの判定など (quiz-based-support から移植)
  ui/          VS Code 側: WebviewViewProvider、Webview との通信プロトコル
  extension.ts 起動処理と公開 API
media/         Webview の JS/CSS、アイコン (依存ライブラリなし)
test/          node:test によるテスト (ツール、エージェントループ、モックAPIに対するプロバイダ、理解の仕組み、画面のホスト)
```

### 拡張ポイント

- **ツールを追加**: `src/tools/` に `Tool` を実装し、`src/tools/index.ts` の一覧に足します。
  `permission` (`none` / `edit` / `execute`) で確認の要否と並列実行の可否が決まります。
- **モデル/APIを追加**: `LLMProvider.complete()` を実装して `src/providers/index.ts` で登録し、`src/config.ts` の `provider` にIDを指定します。
- **別の拡張機能から**: `activate()` の戻り値で同じことができます。

```ts
const grasp = vscode.extensions.getExtension('local.grasp-dev')?.exports;
grasp.registerTool({
  name: 'OpenIssue', description: '…', permission: 'none',
  parameters: { type: 'object', properties: { id: { type: 'number' } }, required: ['id'] },
  async execute(input, ctx) { return { content: '…' }; },
});
```

- **UIを差し替え**: `core/` は `AgentEvent` を emit するだけなので、CLI など別のフロントエンドからも `Agent` をそのまま使えます。
